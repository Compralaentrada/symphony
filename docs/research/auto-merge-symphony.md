# Auto-merge en Symphony

Investigación realizada el 23 de octubre de 2026 sobre el código del repositorio en `b739b98`. Se revisaron la configuración, el pipeline, las herramientas GitHub y el gate de merge. No se ejecutaron tests ni se inspeccionó una instancia desplegada.

## Hallazgo principal

`merge_policy: auto` permite que Review pida al host que fusione una PR. En el backend GitHub Projects, Symphony consulta el estado y las comprobaciones, ejecuta directamente la mutación GraphQL `mergePullRequest` y vuelve a consultar la PR para verificar el merge. No activa la función nativa de GitHub `enablePullRequestAutoMerge`, que deja una PR esperando hasta que se cumplan los requisitos; la mutación de Symphony intenta fusionarla en ese momento. Symphony tampoco aprueba la PR automáticamente. [Gate de Projects](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1518-L1599) · [Referencia GraphQL de GitHub](https://docs.github.com/en/graphql/reference/pulls) · [Auto-merge nativo de GitHub](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request) · [Contrato de configuración](../../elixir/WORKFLOW.md#L48-L48)

El `elixir/WORKFLOW.md` versionado en este repo tiene `merge_policy: auto`, usa `github_projects` y declara el proyecto 9, el repo `Compralaentrada/symphony`, la base `main` y el check `make -C elixir all`. Eso confirma la configuración guardada en el repo, no que un proceso desplegado esté cargando actualmente ese archivo. [WORKFLOW.md](../../elixir/WORKFLOW.md#L1-L27)

## Activación y alcance

- El esquema acepta `human` y `auto`; el valor por defecto es `human`. La clave global `merge_policy` se copia al provider para trackers `github` y `github_projects`. Si la clave global se omite, se conserva un `tracker.provider.merge_policy` explícito; si se define globalmente, prevalece. [Esquema de configuración](../../elixir/lib/symphony_elixir/config/schema.ex#L292-L312) · [Valores permitidos](../../elixir/lib/symphony_elixir/config/schema.ex#L383-L386) · [Resolución de configuración](../../elixir/lib/symphony_elixir/config/schema.ex#L398-L428) · [Precedencia en código](../../elixir/lib/symphony_elixir/config/schema.ex#L468-L470) · [Regla documentada](../../elixir/WORKFLOW.md#L48-L48)
- El host pasa la política al contexto del agente y agrega `request_merge` a las operaciones permitidas en `review` cuando la política es `auto`. La comprobación de `allowed_operations` no filtra por `tracker_kind`; por tanto, también puede aparecer en el esquema de herramienta para GitHub Issues. Sin embargo, solo `GitHub.Projects.Client` implementa esa operación: `GitHub.Client` la rechaza como operación no compatible. En la práctica, el gate funcional es de GitHub Projects, aunque la configuración común acepte ambos trackers. [Contexto de agente](../../elixir/lib/symphony_elixir/agent_runner.ex#L382-L400) · [Exposición por fase](../../elixir/lib/symphony_elixir/github/agent_tool.ex#L134-L145) · [Enrutamiento](../../elixir/lib/symphony_elixir/github/agent_tool.ex#L108-L120) · [Dispatcher GitHub Issues](../../elixir/lib/symphony_elixir/github/client.ex#L57-L79) · [Dispatcher Projects](../../elixir/lib/symphony_elixir/github/projects/client.ex#L388-L415)
- Con la política `human`, Review termina en `Human Review` y espera a la persona. Con `auto`, las instrucciones de Review indican primero entregar `passed`, después llamar `request_merge` y, si el host confirma la fusión, entregar `merged`. [Instrucciones de Review](../../elixir/lib/symphony_elixir/agent_runner.ex#L590-L600) · [Transición local de Review](../../elixir/lib/symphony_elixir/pipeline.ex#L328-L369)

## Flujo de ejecución

1. **Build y QA fijan la entrega.** Build crea o actualiza una PR draft. En QA, Symphony ejecuta los comandos `required_checks` sobre el SHA aceptado; antes y después verifica que `HEAD` siga siendo ese SHA y que el workspace esté limpio. Cada resultado incluye nombre, estado y evidencia. [Creación de PR draft](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1031-L1063) · [Ejecución de checks](../../elixir/lib/symphony_elixir/agent_runner.ex#L337-L379) · [Validación del workspace](../../elixir/lib/symphony_elixir/workspace.ex#L259-L302)
2. **Review prepara la PR.** Un reporte `passed` solo avanza si su SHA coincide con el SHA aceptado y no quedan findings anteriores sin resolver. El host cambia la PR a lista para revisión y el item a `Human Review`; la operación de merge solo admite un item cuyo estado actual sea `Review` o `Human Review`. [Validación y transición del pipeline](../../elixir/lib/symphony_elixir/pipeline.ex#L328-L359) · [Etapa de PR y estado de Review](../../elixir/lib/symphony_elixir/github/projects/client.ex#L939-L946) · [Actualización a lista para revisión](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1093-L1102) · [Estados aceptados por el gate](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1518-L1535)
3. **El host comprueba el gate.** Para `request_merge`, valida que la política sea `auto`, que la fase sea `review`, que el lease del agente siga vigente y que la issue/item de GitHub continúe en uno de los estados permitidos. Después comprueba las condiciones detalladas en la sección siguiente. [Despacho y lease](../../elixir/lib/symphony_elixir/github/projects/client.ex#L388-L415) · [Gate](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1518-L1573)
4. **Fusiona y verifica.** Si la PR sigue abierta y pasa el gate, Symphony llama `mergePullRequest` con `expectedHeadOid` igual al SHA aceptado. Exige que la respuesta incluya `mergedAt` y luego vuelve a leer la PR para comprobar que está fusionada con la rama y base esperadas. Si ya estaba fusionada, omite la mutación y aun así hace la lectura de confirmación. [Mutación y verificación remota](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1575-L1599)
5. **Cierra solo después de verificar.** Review entrega `merged`; el backend vuelve a consultar PR e issue, exige que el merge corresponda a la base y al SHA aceptados, cierra la issue y marca el Project como `Done`. El pipeline valida la evidencia remota de PR fusionada, issue cerrada y Project en `Done` antes de guardar localmente la tarea como completada. [Finalización en Projects](../../elixir/lib/symphony_elixir/github/projects/client.ex#L902-L930) · [Verificación antes de cerrar](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1107-L1129) · [Validación de evidencia en el pipeline](../../elixir/lib/symphony_elixir/pipeline.ex#L761-L843) · [Persistencia de `done`](../../elixir/lib/symphony_elixir/pipeline.ex#L361-L369)

## Qué bloquea el merge

- **Check local de Symphony:** cada comando configurado debe tener `status: passed` y evidencia no vacía. La configuración de pipeline exige al menos un `required_check` por repo. En la QA actual, un check fallido, no disponible, sin evidencia, con SHA distinto o con workspace sucio impide avanzar. [Evaluación de evidencia](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1478-L1483) · [Checks requeridos por repo](../../elixir/lib/symphony_elixir/github/projects/client.ex#L2189-L2229) · [Validación al salir de QA](../../elixir/lib/symphony_elixir/pipeline.ex#L312-L325) · [Workspace y ejecución](../../elixir/lib/symphony_elixir/workspace.ex#L266-L302)
- **Estado remoto de la PR:** el head debe seguir en `task.current_sha`; el `baseRefOid` de la PR debe coincidir con el tip actual de la base; `statusCheckRollup.state` debe ser exactamente `SUCCESS`; y la PR debe estar ya fusionada o abierta y no ser draft. [Predicados de merge](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1550-L1573)
- **Lease, política y estado:** si la llamada no viene del lane Review con política `auto`, el lease no es vigente o el Project cambió fuera de `Review`/`Human Review`, el host rechaza la operación. [Gate y estados](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1518-L1547) · [Validación de lease](../../elixir/lib/symphony_elixir/github/projects/client.ex#L855-L877)
- **GitHub rechaza el merge:** errores de la mutación o falta de `mergedAt` no producen evidencia de merge; una confirmación posterior que no encuentra la PR fusionada también falla. El contrato de GitHub exige permisos de escritura y las reglas de rama pueden requerir aprobaciones, checks, conversaciones resueltas o base actualizada. [Manejo de la mutación](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1575-L1599) · [Requisitos de merge de GitHub](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request) · [Reglas de ramas protegidas](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

El gate de Symphony no consulta explícitamente `reviewDecision`, la configuración de protección de la rama ni los permisos del actor antes de la mutación. Sí evalúa el rollup de checks y los SHA; las revisiones requeridas, permisos y demás reglas dependen de la decisión de GitHub al aceptar o rechazar `mergePullRequest`. No hay en este camino una operación de encolado de merge queue; si la base exige cola, el flujo de Symphony no la solicita explícitamente. GitHub documenta que una rama con merge queue requiere el flujo específico de cola. [Campos consultados y mutación](../../elixir/lib/symphony_elixir/github/projects/client.ex#L108-L124) · [Gate local](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1564-L1589) · [Merge queue de GitHub](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request-with-a-merge-queue)

## Implementado y previsto

El plan del pipeline fija como objetivo: base actualizada, checks requeridos aprobados, revisión del mismo SHA, ningún hallazgo bloqueante y protecciones de rama satisfechas. El código ya comprueba el SHA del reporte de Review, que no queden findings, los checks host y GitHub, que la base no haya avanzado y que la PR no sea draft. La app no inspecciona por separado las reglas de rama ni permisos: deja que la mutación GitHub las aplique. [Criterio del plan](../superboard-symphony-plan.md#L520-L524) · [Detalle técnico pendiente registrado por el plan](../superboard-symphony-plan.md#L605-L608) · [Validación de Review](../../elixir/lib/symphony_elixir/pipeline.ex#L328-L359) · [Gate de Projects](../../elixir/lib/symphony_elixir/github/projects/client.ex#L1518-L1599)

El término “auto-merge” aquí es una política de Symphony para una fusión inmediata mediada por el host. GitHub documenta por separado su auto-merge nativo, y el schema GraphQL también distingue `mergePullRequest` de `enablePullRequestAutoMerge`; Symphony usa el primero. [Mutación usada por Symphony](../../elixir/lib/symphony_elixir/github/projects/client.ex#L119-L124) · [Referencia GraphQL de GitHub](https://docs.github.com/en/graphql/reference/pulls) · [Auto-merge nativo](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request)
